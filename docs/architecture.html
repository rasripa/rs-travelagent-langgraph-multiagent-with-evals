Solution Architecture · Demo Build

Train Travel Agent

A multi-agent rail assistant on Amazon Bedrock AgentCore — a domain-agnostic router, three specialist Tier-2 sub-agents discovered over A2A, three MCP tool servers behind a single governed gateway, and a standalone two-SDK evaluation subsystem.
LangGraph (Python) agents · AgentCore Runtime · AgentCore Gateway + Cedar policy · synthetic data throughout
What this is

A working rail travel assistant that demonstrates the four things customers most often get wrong in multi-agent design: when a capability deserves to be an agent, how agents coordinate, how tool access is isolated per agent, and where policy knowledge belongs.

Everything runs on synthetic data. No real rail APIs, no real passenger records, no payment flows — the tool responses are fixtures shaped like real API payloads so the agent behaviour is faithful without any external dependency.

2. Why this split, and not another

Split by lifecycle, not by domain. The two transactional sub-agents divide on pre-travel versus post-booking, with a third, the Policy Advisor, owning the rules that both of them are judged against. The obvious alternative — splitting by domain, say a Fares Agent and a Timetable Agent — was rejected for two reasons:

  • It gives the agents no legitimate reason to share a tool server, so the shared-server design becomes contrived.
  • It cuts across how travellers actually ask for things. “Book me a train” and “my train is cancelled” are different jobs; “fares” and “timetables” are the same job seen from two angles, and a single query usually needs both.

Agent boundaries should follow query boundaries. A disrupted-journey question touches identity, the existing booking, alternative services and compensation — so those belong together behind one agent, even though they span several backends.

The test we applied, and would apply again: a capability earns its own agent only if it needs its own reasoning loop — multi-step planning, its own context, or an independent release cycle. If it is a single lookup, it is a tool, not an agent. That is precisely why the policy knowledge base sits on the orchestrator as a tool rather than behind a third “Policy Agent”: answering “can I change an Advance ticket?” needs no booking context and no planning, so spawning an agent for it would add a full model round trip for nothing.

Why Traveller Profile is the right server to share

Both agents need it for genuinely different reasons. The Planner needs the railcard to compute correct fares and the home station to default the origin. The Support agent needs the same railcard to compute refund and compensation entitlement, and identity to locate bookings. One dataset, two consumers, two purposes — which is what makes sharing legitimate rather than an artefact of the demo. It is also the only PII-bearing server, which is what makes the access-control story below worth telling.

5. Per-agent tool isolation — the core technical point

Each sub-agent must see only the tools it is entitled to. The naive way to achieve that is a separate MCP server per agent with no sharing — which costs you a unified catalogue, central audit, and one credential boundary, and still leaves no authorization layer. We do it with policy instead.

AgentCore Policy evaluates Cedar on every request, default-deny, and — the part that matters here — it governs discovery as well as invocation. Tools denied by policy do not appear in tools/list at all.

So both sub-agents call the same gateway endpoint and receive different catalogues:

Calling identity tools/list returns Cannot see or call
Journey Planner Journey Search (3) + Traveller Profile 2 of 3 = 5 tools All of Ticket Operations, and get_railcard_and_loyalty on the shared server
Journey Support Ticket Operations (3) + Traveller Profile 1 of 3 = 4 tools All of Journey Search, and get_traveller_profile + list_saved_journeys on the shared server
The Cedar policies, in full
// Planner: journey search + shared profile
permit(
  principal == AgentCore::IamEntity::"arn:aws:sts::<account>:assumed-role/travel-demo-journey-planner-role",
  action in [
    AgentCore::Action::"JourneySearch___search_journeys",
    AgentCore::Action::"JourneySearch___get_fares",
    AgentCore::Action::"JourneySearch___book_ticket",
    AgentCore::Action::"TravellerProfile___get_traveller_profile",
    AgentCore::Action::"TravellerProfile___list_saved_journeys"
  ],
  resource
);

// Support: ticket operations + shared profile
permit(
  principal == AgentCore::IamEntity::"arn:aws:sts::<account>:assumed-role/travel-demo-journey-support-role",
  action in [
    AgentCore::Action::"TicketOperations___get_booking",
    AgentCore::Action::"TicketOperations___change_or_cancel_ticket",
    AgentCore::Action::"TicketOperations___claim_delay_repay",
    AgentCore::Action::"TravellerProfile___get_traveller_profile",
    AgentCore::Action::"TravellerProfile___get_railcard_and_loyalty",
    AgentCore::Action::"TravellerProfile___list_saved_journeys"
  ],
  resource
);

Tool names are target-prefixed by the gateway as TargetName___toolName, which is what makes these policies writable. Cedar is default-deny, so nothing beyond these two statements is reachable by either agent — and forbid would override permit if we later needed an exception.

Two limits to state honestly in the walkthrough.
  • Listing is a meta-action. A principal may list a tool if any circumstance would permit calling it. So a parameter-conditional restriction (for example, refunds only below a threshold) leaves the tool visible while still denying the out-of-bounds call. To hide such a tool entirely you add a RESPONSE interceptor. Our policies are unconditional, so filtering here is absolute.
  • Policy covers MCP tools only. MCP prompts and resources are always allowed regardless of policy, and are auto-synced into the catalogue if a server advertises them. Our three servers therefore expose tools only — a deliberate design constraint, not an accident.

6. A2A on the agent plane

Two planes, deliberately separate. A2A carries agent-to-agent delegation; MCP carries agent-to-tool access. This matches the Well-Architected Agentic AI Lens guidance to use “MCP for tool integration, A2A for agent-to-agent coordination.” AgentCore Gateway is an MCP gateway, not an A2A router — so A2A here is Runtime-to-Runtime and does not pass through the gateway.

Three A2A paths, and they all start at the router:

  • Train Travel Agent → Journey Planner — “plan and book this trip”
  • Train Travel Agent → Journey Support — “deal with this booking problem”
  • Train Travel Agent → Policy Advisor — “what do the rules say”

There is deliberately no fourth path. An earlier revision had Journey Support delegate to the Journey Planner during disruption, which read well — a genuine peer delegation, a task handed over and an artifact returned. It was the wrong shape. A peer edge couples two Tier-2 agents: the team that owns Support can no longer change its interface without checking who else calls it, which is the developmental bottleneck a multi-agent split exists to remove. It also puts routing logic inside a domain agent, where no platform team can see it.

So Tier 2 is a set of leaves. When a request needs two capabilities — the entitlement rule and the action on the booking — Support reports that a search is required and the router fans out to the Planner, then joins the answers. One extra hop through Tier 1 buys a topology where every edge is visible at the router and no Tier-2 agent knows another exists. The constraint is enforced by IAM, not by convention: no sub-agent role grants InvokeAgentRuntime on a peer.

Discovery is what makes this loose rather than merely hub-and-spoke. The router holds no hardcoded delegation tools. At startup it reads a sub-agents registry, fetches each agent’s card from /.well-known/agent-card.json, and synthesises one tool per agent whose description is built from the AgentSkill entries that card advertises — id, name, description, tags and examples. The model then routes by reading tool descriptions, the same mechanism it uses for every other tool. Adding a Tier-2 agent is a deployment plus one registry entry; the router is not redeployed and not edited. An unreachable card is skipped with a warning rather than failing startup, because one sick Tier-2 agent must not take the assistant down.

Trap to avoid: do not set time_of_last_update to the current time on every ping. A timestamp that advances each ping signals continuous status change, the idle-session timeout never fires, and sessions persist to MaxLifetime and exhaust the session quota.

The LangGraph cost, stated plainly. Strands ships a built-in StrandsA2AExecutor that wraps an agent and auto-builds its Agent Card. LangGraph has no equivalent, and remote A2A agents are not native LangGraph nodes — so we write both halves: an AgentExecutor on each sub-agent that invokes the compiled graph and maps its output onto A2A events, and an A2A client in the callers. This is real work and it is the main reason to adopt A2A only where it earns its place.
Also: the A2A samples use an in-memory task store, which will not survive AgentCore's per-session microVMs. For the demo that is acceptable; for production a durable task store is required if you depend on task lifecycle across turns.

7. Policy & FAQ knowledge base

A single tool on the orchestrator, backed by five synthetic policy documents. Rail fare rules are genuinely intricate, which makes retrieval the right mechanism rather than prompt-stuffing.

DocumentCovers
fare-rules.mdAdvance / Off-Peak / Anytime: flexibility, refundability, change fees, break of journey
railcards.mdRailcard types, discounts, eligibility, minimum fares, time restrictions
delay-repay.mdDelay bands and compensation percentages, claim window, evidence, payment methods
luggage-and-accessibility.mdLuggage allowance, bicycles, assisted travel booking, wheelchair spaces
ticket-validity.mdValidity windows, routing restrictions, peak definitions, split ticketing

Implementation: an Amazon Bedrock MANAGED Knowledge Base, attached to the same AgentCore Gateway as the MCP servers through the built-in bedrock-knowledge-bases connector. MANAGED means Bedrock owns the vector store, so there is no OpenSearch collection or Aurora cluster to provision, scale or pay for while idle — and it is a hard requirement, because the gateway connector supports managed knowledge bases only. The five markdown files are ingested inline via a CUSTOM data source, straight from the repo, with no S3 staging bucket for content.

The connector exposes two tools: Retrieve (one hybrid search, returning passages with sources) and AgenticRetrieveStream (multi-step planning with a synthesised, citation-backed answer). Cedar grants the orchestrator only Retrieve — fast, cheap and deterministic, which is what a scripted demo wants. Denying AgenticRetrieveStream is a second illustration of per-tool control, here capping cost and latency rather than protecting data. The knowledge base id never reaches the agent; the gateway binds it, so swapping or scaling the knowledge base changes no agent code.

Local fallback: with TRAVEL_RUN_MODE=local the same five documents are chunked, embedded with Titan and cached to a JSON file, retrieved by cosine similarity in process. The agent-facing interface is identical, so the demo still runs on a laptop with nothing provisioned.

Why the KB moved OFF the orchestrator. An earlier revision kept it on the router, on the reasoning that a policy question resolves in one model turn and wrapping a lookup in an agentic loop costs a whole extra inference. That reasoning is sound on latency and wrong on ownership: it made Tier 1 a domain participant, holding rail-specific knowledge and needing a rail-specific prompt, so a platform team could not own the router and hand new domains to other teams. The knowledge base now belongs to the Policy Advisor, a Tier-2 agent like any other. The cost is one extra A2A hop on policy questions; the gain is a router whose only job is routing. When the organisational boundary and the latency argument disagree, the organisational boundary is the one that compounds.

8. Identity and authorization chain

Every hop authenticates, and the per-agent identity is what makes the tool isolation in §5 enforceable rather than advisory.

Hop Mechanism
Traveller → Train Travel AgentRuntime inbound auth — SigV4 (IAM)
Orchestrator → sub-agents (A2A)SigV4, signed with the orchestrator's own IAM execution role. Each sub-agent runtime keeps the default IAM inbound auth, and the orchestrator's role grants bedrock-agentcore:InvokeAgentRuntime on only the two sub-agent runtimes.
Sub-agent → sub-agentDoes not exist. No sub-agent role grants InvokeAgentRuntime on a peer, so the topology is enforced by IAM and not merely by convention. A request needing two capabilities is fanned out by the router.
Two IAM details that biteAn A2A caller needs two actions, not one: bedrock-agentcore:InvokeAgentRuntime and bedrock-agentcore:GetAgentCard, because the client reads the agent card before it can send a task. Missing the second gives a 403 on /.well-known/agent-card.json that looks like an invoke failure. And the invoke is authorized against the endpoint-qualified ARN runtime/<id>/runtime-endpoint/<qualifier>, so a policy listing only the bare runtime ARN denies it.
Sub-agent → Gateway (MCP)SigV4 under each sub-agent's own IAM execution role — that role ARN becomes the Cedar principal (AgentCore::IamEntity). One role per sub-agent is mandatory: a shared role would be indistinguishable to Cedar and the per-agent filtering below would be unenforceable.
Inside the GatewayCedar policy engine, default-deny — roll out in LOG_ONLY, inspect decisions, then ENFORCE
Gateway → MCP serversIAM / SigV4 via the gateway service role — available because the MCP servers run on AgentCore Runtime, which natively verifies SigV4
A deliberate simplification worth calling out. Because the MCP servers sit on AgentCore Runtime rather than behind a load balancer, outbound auth can be IAM/SigV4 — no OAuth client or API key to provision for the tool hop. Had we put them on ECS behind an ALB, SigV4 would not be an option (an ALB cannot verify SigV4 signatures) and we would have needed OAuth client-credentials or an API key per target. Inbound is IAM too, so this build is IAM end to end: no user pool, no token endpoint, and no client secret stored anywhere. Note that mcpServer targets need an explicit iamCredentialProvider with service: bedrock-agentcore — credentialProviderType alone is not enough, unlike Lambda or API Gateway targets.
Not in the demo, required in production: per-user scoping. Today the Support agent's identity authorises the tool call, so it could in principle retrieve any booking. Production would use on-behalf-of token exchange so the exchanged token carries both the traveller's and the agent's identity, letting Ticket Operations enforce “this traveller, this booking” itself. Likewise, change_or_cancel_ticket and claim_delay_repay are irreversible and money-moving: the Lens calls for human-in-the-loop confirmation on exactly these, which we surface as an explicit confirmation turn rather than protocol-level enforcement.

9. Observability — and how it is actually switched on

The failure mode that cost the most time

Shipping aws-opentelemetry-distro in the package and setting OTEL_PYTHON_DISTRO / OTEL_PYTHON_CONFIGURATOR is not enough. Those variables are read only by the OpenTelemetry launcher (opentelemetry-instrument), and a direct-code deployment has no shell wrapper to run it. The library sat in the zip, unused: HTTP spans only, no model spans, no token counts — and the Bedrock AgentCore Observability dashboard reported 0 agents while everything else looked healthy.

The launcher does nothing more than prepend its own directory to PYTHONPATH and re-exec. So the deploy does that directly, and Python imports that directory’s sitecustomize.py at interpreter startup:

PYTHONPATH=/var/task/opentelemetry/instrumentation/auto_instrumentation:/var/task
  • What the launcher brings. Loading sitecustomize activates the AWS distro, the AWS configurator and every matching instrumentor. That is what produces the spans the dashboard reads — amazon.opentelemetry.distro.instrumentation.langchain (agent turns, gen_ai.* attributes, token counts), opentelemetry.instrumentation.botocore.bedrock-runtime (the Bedrock Converse calls), amazon.opentelemetry.distro.instrumentation.mcp (tool calls), plus httpx and Starlette for the A2A hops. Verified in aws/spans: gen_ai.usage.input_tokens=4384, output_tokens=150, aws.genai.token_count_total=4534.
  • Adopt, never compete. observability.adot_already_configured() detects that the launcher ran and adopts the pipeline. OpenTelemetry refuses to override an existing TracerProvider, so building a second one would leave the richer ADOT pipeline in place while our exporter silently sent nothing. The hand-rolled provider remains as the local / non-AWS fallback.
  • aws.log.group.names must be the real log group — /aws/bedrock-agentcore/runtimes/<runtimeId>-DEFAULT. The runtime ID is assigned at creation, so it cannot be derived from the name; deploy.py reads it from the existing runtime and performs one corrective update for a brand-new one. This attribute is how CloudWatch indexes telemetry under the AgentCore dashboard: point it at a log group that does not exist and spans still arrive in aws/spans, but are never tied to the runtime. deploy.py verify now asserts this for all six runtimes.
  • service.name must match the runtime name, so the deployed environment value wins over the readable label the servers pass locally.
  • OTLP log export is off (OTEL_LOGS_EXPORTER=none). It is redundant: AgentCore already captures stdout into the runtime log group, and the dashboard is driven by spans. Left on it ships a duplicate copy of the logs and rejects every batch with 400 … The specified log stream does not exist once per second unless a fixed stream is pre-created.
  • Two variables deliberately unset. OTEL_EXPORTER_OTLP_TRACES_ENDPOINT — the distro derives the regional X-Ray endpoint itself and only via setdefault, so hardcoding one overrides it. OTEL_EXPORTER_OTLP_TRACES_HEADERS — redirecting spans to your own log group additionally needs a CloudWatch Logs resource policy letting xray.amazonaws.com call logs:PutLogEvents, without which they are silently lost.
  • Account-wide prerequisite. CloudWatch Transaction Search must be enabled and the X-Ray trace-segment destination pointed at CloudWatch Logs, or the OTLP traces endpoint rejects the spans. deploy.py preflight reports it rather than changing it.
  • One trace, many spans. A disruption query crossing orchestrator → Support → Planner → gateway → two MCP servers arrives as one trace. A composite propagator accepts and emits both W3C traceparent and X-Ray headers, because a mixed-propagator mesh is the usual reason a multi-agent trace fragments.
  • Privacy note. Vended gateway logs can include request and response bodies — traveller profile data here. Scope access and retention deliberately, even with synthetic data.

Two conclusions worth stating out loud: warm gateway calls are 20–140 ms, so Cedar authorization adds no measurable latency — the per-tool policy layer is free at runtime. And end-to-end latency is dominated by the fan-out, not the plumbing: per-case p50 14–15.5s, p95 43–46s, p99 47–55s, where a direct sub-agent call is 8–20s but a router turn that delegates to two sub-agents runs 35–55s. Cold containers add roughly 8s per sub-agent and 4–5s per MCP runtime on top. Client read timeouts must allow for the upper bound: botocore defaults to 60s, which is below it, so both invoke.py and the frontend proxy set read_timeout=300 with retries disabled.

10. Synthetic data design

All data is fictional. Tool responses are shaped like plausible rail API payloads so agent reasoning is realistic, but nothing connects to a real retailer, operator or payment system.

Fixture Shape and coverage
Travellers3 profiles with different railcards (Two Together, 16–25, none) and loyalty tiers, so fare and refund maths visibly differ between them. One has accessibility requirements.
Stations & routes8 major stations, a handful of realistic corridors (London–Manchester, London–Edinburgh, Manchester–Leeds) with plausible journey times, operators and change patterns.
Services & faresTimetabled departures across the day with Advance / Off-Peak / Anytime pricing in two classes. Advance is cheap and non-refundable; Anytime is expensive and fully flexible — the contrast drives the policy conversation.
Bookings4 existing bookings deliberately spanning the interesting cases: a refundable Anytime, a non-refundable Advance, one on a cancelled service, and one already delayed past the compensation threshold.

The design rule for the fixtures: every demo beat must be deterministic. Nothing is randomised, no response depends on the current clock beyond a fixed reference date, and the seeded disruption is always present. A live demo should never rely on luck.

11. Running it — two modes

Before either mode — environment setup

Python 3.12. Create the virtual environment and install the pinned dependencies before deploying any change: the packager vendors dependencies out of requirements.txt, so the local environment and the deployed artifact must agree.

uv venv --python 3.12 .venv uv pip install -r requirements.txt # or: python3.12 -m venv .venv && .venv/bin/python -m pip install -r requirements.txt .venv/bin/python -c "import langgraph, a2a, mcp, boto3, amazon.opentelemetry.distro; print('ok')"

Three pins are deliberate: mcp==1.30.0 and a2a-sdk==0.3.26 (the 2.x and 1.x lines changed their client APIs), and aws-opentelemetry-distro==0.21.0, which supplies the X-Ray ID generator, the SigV4 span exporter and the LangChain/MCP agentic instrumentation that CloudWatch GenAI Observability reads.

Local mode — the demo safety net
  • Three MCP servers as local processes over streamable HTTP
  • Three LangGraph agents in-process, A2A over localhost
  • Tool access filtered by a local policy shim that mirrors the Cedar statements
  • Bedrock is the only AWS dependency (model + embeddings)
  • One command, no deploy, nothing to break on the day
AgentCore mode — the real thing
  • Six AgentCore Runtimes: 3 agents (A2A protocol) + 3 MCP servers (MCP protocol)
  • One Gateway, four targets — three mcpServer plus a managed-knowledge-base connector — SigV4 outbound
  • Seven IAM roles: one per agent (3), plus the shared MCP runtime role, the gateway role, the knowledge-base role and the memory role
  • Policy engine with three Cedar policies (one per agent), LOG_ONLY → ENFORCE
  • Transaction Search + the ADOT launcher on PYTHONPATH for the unified trace (§9)
  • AgentCore Memory on the orchestrator, and six Parameter Store entries read at use time
Sequencing recommendation. Build and rehearse in local mode first. Deploy to AgentCore as a second pass, and treat the deployed environment as the preferred demo path with local as the fallback you can switch to in seconds. Standing up six runtimes, a gateway and Cedar for the first time hours before a customer session is the single largest risk in this plan — the local path removes it entirely.

13. Evaluating the agents

Structural tests prove nothing is wired wrong. They cannot tell you whether an agent reasons well, refuses what it should, or quietly invents a refund rule. That needs scoring, and scoring an agent means judging free text — so the judge is itself a model.

  • Two SDKs, deliberately. strands-agents-evals and LangSmith run offline over the same 31 cases. A single judge is one model’s opinion; two judges disagreeing is a signal worth reading. Across two sweeps each against the deployed runtimes they scored 76.6–80.2% (LangSmith) and 77.2–78.4% (Strands) overall, while agreeing to three decimal places at 0.897 on responsible AI in the latest pair — which is itself a finding about evaluator stability.
  • Each tier is evaluated on its own terms. Sub-agents are scored directly over A2A, the router end to end. That matters operationally: you can score one sub-agent after changing it without standing up the whole system or freezing a staging environment.
  • Quality and responsible AI are separate categories. Quality: correctness, faithfulness, helpfulness, relevance, instruction-following, plus a ground-truth rubric bound to the fixtures. Responsible AI: harmfulness, stereotyping and appropriate refusal, over 8 adversarial probes — prompt injection, attempted extraction of another traveller’s data, a request for card details, out-of-domain refusal, an attempt to falsify a compensation claim, and a leading question inviting a confidently wrong policy answer.
  • Ground truth comes from the fixtures, so the assertions are real rather than vibes: £24.64 for the discounted Advance, £14.99 Delay Repay, AW0715-20261106 always cancelled.
  • Zero changes to application code. The subsystem has its own virtual environment and its own pinned dependencies, and the frontend shells out to that interpreter rather than importing it. Nothing in evaluation/ reaches the deployment package — the packager vendors requirements.txt, and a judge model has no business shipping to production.

What this run shows, beyond the headline
  • faithfulness splits the judges hardest: LangSmith 0.75–0.77, Strands 0.36–0.52. The gap is not noise — it is the two SDKs disagreeing about what “grounded in the retrieved context” means, Strands’ five-point semantic scale being markedly stricter. This is the case for two judges in one line: a single runner would have reported faithfulness as either acceptable or alarming, and you would have believed it.
  • The per-agent breakdown localises the weakness. journey_planner passes only 0.47–0.56 and is the worst agent in every sweep run so far, against policy_advisor 0.83–1.00, journey_support 0.68–0.85 and train_travel_agent 0.84–0.86. Two independent judges ranking the same agent worst, repeatedly, is a finding about the agent rather than judge variance — which is where to look, rather than at the aggregate.
What it found, which is the point: one case fails in both judges — asked for another traveller’s profile on the strength of an unverified “I’m booking on their behalf”, the Journey Planner disclosed that traveller’s name, email, railcard and saved journeys. Cedar cannot close this: get_traveller_profile is legitimately granted to the Planner, and the missing control is which row — which needs on-behalf-of token exchange or a tool-level check that the requested traveller matches the session actor. §8 described that gap as a production requirement. The evaluation turned it from an assertion into a reproducible exploit, which is exactly what this layer is for.

4 Switch to a terminal. The security beat. Call tools/list with the Planner's token, then the Support token, and diff: six tools each, three shared, three different. 15. Implementation notes that are not visible in the code

Each of these failed silently or misleadingly during the build. They are the reason the test suite and deploy.py verify are shaped the way they are, and they are the first things to check when something behaves oddly.

TrapDetail
A callable model does not get tools boundcreate_react_agent binds tools itself only for a static model. We pass a callable so the model id is re-read each turn, and on that path LangGraph uses the return value verbatim — so the callable must do model.bind_tools(tools). Omit it and there is no error: the model never sees the tool schemas and, because the prompt still lists them, it imitates the provider’s function-call syntax as prose. Guarded by test_tools_are_bound_to_the_model.
GetAgentCard is a separate IAM actionAn A2A client fetches /.well-known/agent-card.json before it can send anything, which needs bedrock-agentcore:GetAgentCard — not InvokeAgentRuntime. Without it delegation fails as a 403 on the card URL, which reads like an invoke-permission problem and is not.
Invoke authorizes on the endpoint ARNThe resource is runtime/<id>/runtime-endpoint/<qualifier>, not the bare runtime/<id>. Confirm with aws iam simulate-principal-policy against both forms before concluding a policy is right.
AgentCore discards the container’s response bodyA deliberate 400 reaches the caller as an opaque RuntimeClientError … check your CloudWatch logs — and if the handler did not log, CloudWatch has nothing either. Every rejection path in the orchestrator therefore logs. The usual cause is a missing actor_id, which is mandatory whenever memory is enabled.
Environment beats Parameter StoreResolution is env → SSM → default, so the deployed runtimes must not set the dynamic values — an env var would pin them to deploy-day values and make the parameter inert. The only A2A URL a runtime sets is its own, for its agent card.
The agent card must advertise the deployed URLA card saying 0.0.0.0:9000 resolves fine and then every delegation fails, because A2A clients route by card.url. The URL derives from the runtime ARN, which does not exist until creation — hence a two-phase environment update.
Two naming conventions in one APIGateways and targets allow hyphens (([0-9a-zA-Z][-]?){1,48}); policy engines, policies, runtimes and memory do not ([A-Za-z][A-Za-z0-9_]{0,47}). Hence PREFIX and PREFIX_U; preflight validates all 16 names against patterns read from the botocore model.
Cedar rejects bare protocol actionsThe engine parses every action as Target___tool, so initialize and tools/list are rejected outright — the handshake is permitted implicitly. A published example includes them, but it uses JWT inbound.
Target credential config is not uniformmcpServer and openApiSchema targets require iamCredentialProvider; Lambda, API Gateway, Smithy and connector targets must omit it. A wrong shape is a validation error, not a warning.
Managed-KB data source shapetype: "MANAGED_KNOWLEDGE_BASE_CONNECTOR" with the connector in connectorParameters — not the plain type: "CUSTOM" used by self-managed knowledge bases.
Packaging verifies itselfAn exclusion rule once matched everything and produced a 22-byte zip; the ARM64 check passed vacuously on an empty set. The packager now fails on zero files, zero native extensions, or a missing entrypoint — 6 entrypoints and 28 support paths are checked explicitly.
Documented fields that are wrongThe Memory guide shows conversationalMessage; the real field is conversational with an uppercase role enum and a required eventTimestamp. ListMemories returns no name.
The pattern across all of them: every one produced a healthy-looking system. A green deploy, HTTP 200, spans in the log group, a confident-sounding answer. The lesson that shaped the tooling is that absence of an error is not evidence of correctness — so preflight validates names, package inspects its own artifact, agents asserts the config set is complete, and verify checks both Cedar filtering and the observability wiring on every run.

16. Best practices applied

Practice How it shows up here
Authorise outside agent codeCedar at the gateway, evaluated before any tool executes — so it holds regardless of what the model is persuaded to attempt. Prompt-level restriction is not a control.
Least privilege per agentOne identity per agent, one policy statement per agent, six tools visible instead of nine.
Secrets never in the agentThe gateway holds backend credentials; agents hold none. Here that is the gateway service role signing SigV4 to the MCP runtimes.
Tool catalogue stays smallSix tools per agent, well inside the range where model tool selection stays accurate. Policy filtering is doing double duty as a context-size control.
Don't create an agent for a lookupThe knowledge base is a tool on the orchestrator, not a third sub-agent — saving a full agentic loop on every policy question.
Protocol per boundaryA2A between agents, MCP between agent and tools — matching the Lens guidance rather than forcing one protocol to do both jobs.
Policy rollout disciplineLOG_ONLY first to observe decisions against real traffic, then ENFORCE. Never enforce an unobserved policy.
One trace per requestW3C trace context propagated across A2A hops so a multi-agent turn is a single trace.
Deterministic demo fixturesSeeded disruption and fixed reference date, so no beat depends on chance.
